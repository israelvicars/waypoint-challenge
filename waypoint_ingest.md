# How Waypoint Ingests and Chunks Documents

---

## The problem ingestion solves

An IEP is a 20+ page legal document. A lesson plan is another 8–10 pages. Passing both in full to an AI assistant on every teacher request creates three compounding problems:

1. **Slow and expensive.** Repeated full-document reads add up at scale.
2. **Noisy context.** Most of the IEP — administrative tables, meeting dates, service delivery schedules — is irrelevant to "what should I do differently for this student during the vocabulary warm-up?" Irrelevant text dilutes the model's attention.
3. **Doesn't scale.** A real teacher has 15–18 students with IEPs across five periods. If each student adds 30 pages to the context, the system breaks before it reaches a classroom.

Ingestion converts raw PDFs into a format optimized for AI reasoning — not just human reading.

---

## What ingestion does

When a document is ingested, Waypoint sends the PDF directly to Claude (`claude-opus-4-7`) with a schema-specific extraction prompt. The model reads both text and visual layout — tables, section headers, bullet structures — and produces a structured markdown file organized for downstream use.

This runs **once per document**, not on every teacher request. The output is saved and reused.

---

## The chunking strategy: four tiers

Different questions require different depths of IEP access. Rather than treating the IEP as one monolithic document, Waypoint pre-slices it into four tiers at ingestion time:

| Tier | What it contains | Size | When it's used |
|---|---|---|---|
| **1 — Key Profile Summary** | Synthesized digest: disability classification, present levels by domain, all active goals with baselines and targets, accommodations as a flat list, behavioral patterns (signals to watch for, engagement strategies that work) | ~300 words | Every generation call — always loaded |
| **2 — Goal records** | One section per IEP goal with exact baseline, annual target, measurement criteria, and benchmarks | ~150 words each | On demand, when citing or verifying a specific goal |
| **3 — Accommodation list** | Flat bulleted list of every active accommodation | ~100 words | On demand, for the before-class preparation checklist |
| **4 — Full document** | Complete structured IEP markdown | ~2,500 words | Fallback only — when a specific question requires the full record |

### Why the Key Profile Summary is the pivotal decision

The Key Profile Summary (Tier 1) does not exist in the real IEP. It is generated by Claude *at ingestion time* as a synthesized answer to the question: **"What does a teacher need to know about this student to modify tomorrow's lesson?"**

Because it is generated once at ingestion — not re-generated on every teacher request — the synthesis cost is paid once and the result is stored. At runtime, the system loads the pre-written summary (a string slice, not a new API call) alongside the full lesson and passes both to the model.

For a class with two IEP students, the generation context is:
- Lesson content: ~2,600 words
- Two Key Profile Summaries: ~600 words combined
- **Total: ~3,200 words of signal**

The full IEPs (2 × 2,500 words = 5,000 words) never enter the context unless specifically needed. As class size grows toward 15–18 students, context grows by KPS size (~300 words per student) — not by full IEP size. This is what makes the system viable at real classroom scale.

## How the lesson is ingested

Lesson ingestion follows a complementary principle: **verbatim preservation**.

A modification guide is only useful if it references the actual questions a student will encounter. "Scaffold the reading comprehension activity" is not actionable. "For DRQ-1B, replace the open prompt with this sentence frame: *The author claims ___ because ___*" is.

To enable that specificity, the lesson ingestion pipeline:
- Copies every question stem and passage excerpt word-for-word from the source
- Assigns each question a normalized ID (`DRQ-1A`, `MC-3`, `SR-1`, `DISC-2`)
- Preserves the exact activity sequence, timing, and modality labels

These IDs become the contract between the lesson document and the modification guide. Every recommendation in a generated guide cites a real question by ID. This is also programmatically verifiable — if no question IDs appear in the output, something went wrong upstream.

---

## The end-to-end flow

```
PDF (IEP or lesson)
    ↓
  ingest_iep / ingest_lesson  (one-time, writes to data/)
    ↓
Structured markdown — four tiers (IEP) or verbatim question IDs (lesson)
    ↓
  generate_modifications  (teacher request)
    ↓
Lesson + Key Profile Summaries → claude-opus-4-7 generates modification guide
    ↓
Before-class checklist, per-activity modifications with copy-paste scaffolds,
citation tags tracing each recommendation to a specific IEP goal or accommodation
```

Ingestion and generation are deliberately separated. A teacher's request for a modification guide should be fast — it should not re-read, re-parse, or re-synthesize the IEP. That work is done once at ingestion and the results are available immediately when the teacher needs them.
